What it is: a web platform where faculty upload or enter marks (CTs, FTs, quizzes,
assignments, labs) at question level, and the system automatically computes statistics,
topic mastery, student trends and academic-attention flags.
Problem solved: faculty currently spend hours per assessment cycle in spreadsheets,
and still cannot easily see which topics a section is weak in, which students are
declining, or whether a remedial session helped.
Users: HOD/Admin (department oversight), Faculty (daily use), Students (optional,
read-only, V2).
Why useful: one upload replaces manual averaging, charting and shortlisting; every
number is traceable to the marks behind it.
What makes it different: it closes the loop. A marks system stores data; ACADLYTICS
answers what happened, why, who is affected, what to do, and whether it worked —
through question-to-topic mapping, rule-based attention flags with visible reasons,
and intervention outcome tracking against a peer baseline.
Design principle: deterministic analytics first; AI only narrates verified numbers, never
produces them.
2. Problem Statement
Faculty in a CSE department manage academic data for 2–4 sections per course in
disconnected spreadsheets, and the analysis that should drive teaching decisions is
either done late, done manually, or not done at all.
Current workflow
1. Faculty conducts CT-1, evaluates scripts question by question.
2. Marks go into a personal Excel file per section (layouts differ per faculty).
3. Faculty computes totals, averages, pass % manually or with ad-hoc formulas.
4. Marks are re-typed or copied into the institutional portal.
5. Section comparison and HOD reports are compiled by hand at the end of term.
Problems with spreadsheets
No single source of truth; files are duplicated, emailed and overwritten.
No validation: wrong register numbers, marks above maximum and duplicate rows go
unnoticed.
Absent vs zero is inconsistent across files.
No access control or audit trail on sensitive student data.

Problems with manual analysis
Each new assessment means redoing formulas and charts.
Cross-section and cross-assessment comparison requires merging files.
Analysis happens after the teaching window where it could have helped.
Specific gaps
Weak topics: question-wise marks exist on paper but are rarely mapped to syllabus
topics, so faculty cannot say "Section B is weak in Recursion" with evidence.
Student trends: a student sliding from 78% to 52% across three assessments is
invisible when each assessment is a separate sheet.
Interventions: remedial sessions happen, but nobody records who attended or
compares performance afterwards, so the department cannot learn what works.
3. Proposed Solution
ACADLYTICS replaces the spreadsheet workflow with a validated pipeline that ends in a
measurable action.
flowchart LR
  A[Data<br/>Excel / manual entry] --> B[Processing<br/>validate, match, 
store]
  B --> C[Analytics<br/>stats, topics, trends]
  C --> D[Insights<br/>weak topics, attention flags]
  D --> E[Intervention<br/>faculty action on a student group]
  E --> F[Measurement<br/>net change vs peers]
  F -.next assessment.-> A
The loop restarts with every assessment, so each intervention is measured on real follow-
up data.

9. System Architecture
A modular monolith: one React SPA, one FastAPI service split into domain modules, one
PostgreSQL database. This is the right size for 4 developers and 8 weeks.
9.1 Layered view
flowchart TD
  UI[React + TS SPA<br/>Tailwind, Recharts, TanStack Query] --> API[FastAPI 
routers<br/>/api/v1]
  API --> AUTH[Auth dependency<br/>JWT + RBAC + scope]
  AUTH --> SVC[Service layer<br/>business rules]
  SVC --> ANA[Analytics engine<br/>pure functions]
  SVC --> REPO[Repository layer<br/>SQLAlchemy 2.0]
  ANA --> REPO
  REPO --> DB[(PostgreSQL 16)]
Routers never touch the database directly; analytics functions take plain data in and
return plain data out, so they are unit-testable without a database.

9.5 Key technical decisions
Compute strategy: analytics are computed on write, not on every read. After an
import or mark edit, the service recomputes student_assessment_summary  and
student_topic_summary  rows for that assessment, then re-evaluates attention flags
for that offering. Dashboards read these small tables. At our scale this takes well under
a second, so no job queue.
Contracts: FastAPI generates OpenAPI; frontend generates TypeScript types with
openapi-typescript . One source of truth.
Migrations: Alembic, owned by one person (M1), reviewed by all.
Frontend state: TanStack Query for server state; no Redux.
PDF: HTML templates (Jinja2) → WeasyPrint, so report layout is just HTML/CSS.
Deployment: docker-compose (nginx + api + postgres) on one VM (AWS EC2 t3.small /
Azure B1ms). Optional: managed Postgres (RDS / Azure Database).

10.3 Design notes
marks  is the only source of truth. Both summary tables can be dropped and rebuilt
from it at any time ( POST /admin/recompute ).
Indexes: marks(question_id) , students(section_id) , assessments(offering_id,
sequence_no) , student_topic_summary(topic_id, assessment_id) , trigram index
on students.name  for search.
Enums as PostgreSQL enums or CHECK constraints; keep them in one enums.py
shared with the frontend via OpenAPI.
Students changing section next semester: new section row per term,
students.section_id  updated; historical data is safe because marks link to questions
→ assessments → offerings, not to the student's current section.

12.4 Question difficulty and discrimination
Difficulty index p = mean of x/m over present students (0 to 1). Bands: p ≥ 0.80 Easy, 0.50–
0.79 Moderate, 0.30–0.49 Difficult, < 0.30 Very difficult.
Discrimination (V2) uses the classical upper–lower 27% method: rank students by
assessment total, take top 27% (U) and bottom 27% (L).
D_q = \bar{p}_{q,U} - \bar{p}_{q,L}
Interpretation: D ≥ 0.40 very good, 0.30–0.39 good, 0.20–0.29 marginal, < 0.20 review
question, negative = likely flawed (strong students did worse). Only shown when n ≥ 20.
This is explainable in one sentence, which is why it's included; point-biserial correlation is
not needed.
12.5 Trend classification
Uses the student's P series over assessments in the offering, ordered by sequence_no.
if completed_assessments < 2: label = "Insufficient data"
elif completed_assessments == 2: slope = P[-1] - P[-2]
else: slope = least_squares_slope(x = 1..k, y = P)   # pp per assessment
if slope >= +TREND_DELTA (default 5): "Improving"
elif slope <= -TREND_DELTA: "Declining"
else: "Stable"
The UI shows: "Declining: scores fell by 7.5 percentage points per assessment across CT1,
CT2, FT1 (threshold 5)."
Caveat to state in the report: comparing raw % across assessments ignores difficulty
differences. Optional refinement (V2): use each student's z-score within the assessment
instead of raw %, so a hard CT2 does not make everyone "decline".

prev_mean = mean(P over all earlier assessments)
drop = P_latest - prev_mean
sharp_decline = drop <= -DECLINE_DROP (default 15)

12.7 Academic attention rules
Rules are data ( settings ), not code branches. Each fired rule becomes a factor on the
flag.
A student is listed as Requiring academic attention if any High rule fires or ≥ 2 Medium
rules fire. Display text: "Flagged for additional academic support based on: overall 44%

12.8 Intervention outcome
For intervention on topic t with target group G, peers N (other active students in the
offering), baseline assessment set B and follow-up assessment F:
\Delta_G = \overline{TS}_{G,t}(F) - \overline{TS}_{G,t}(B), \quad \Delta_N = 
\overline{TS}_{N,t}(F) - \overline{TS}_{N,t}(B), \quad \text{Net} = \Delta_G 
- \Delta_N
Shown as: "Targeted students improved 42% → 67% (+25 pp); other students changed +6
pp; net +19 pp. Observational — not a controlled experiment." Only students with data in
both B and F are counted; n is shown. Requires the follow-up assessment to contain at
least one question mapped to t.

13. Excel Import Architecture
The import never writes marks until the faculty confirms, and the confirm is a single
database transaction.
stateDiagram-v2
  [*] --> Uploaded
  Uploaded --> Parsed: read sheet
  Parsed --> Rejected: header/format error
  Parsed --> Previewed: row validation
  Previewed --> Previewed: fix or exclude rows
  Previewed --> Committed: confirm (0 blocking errors)

13.1 Steps
1. Template (recommended path): faculty downloads a template generated from the
assessment — columns Register No | Name | Q1 | Q2 | … , row 2 shows max
marks, data validation on cells. Most errors never happen.
2. Upload: multipart, ≤ 5 MB, .xlsx / .csv  only, MIME + extension check.
3. Parse: pandas read_excel(engine="openpyxl", dtype=str) ; strip whitespace;
normalise headers (case-insensitive, "Q1", "Q 1", "q1" → Q1); detect header row within
first 5 rows.
4. Column mapping: auto-map Q-columns to question labels. Unmapped columns →
faculty maps them in the UI (dropdown). Extra columns ignored with a warning.
5. Validate each row (below) → staged in import_batches.rows  JSONB with per-cell
status.
6. Preview: summary counters + table with red/amber cells; filter "errors only".
7. Fix / exclude: inline edit a cell or tick "exclude row"; revalidate that row server-side.
8. Confirm: allowed only when blocking errors = 0 (after fixes/exclusions). Upsert marks
in one transaction; write audit rows; mark batch committed.
9. Recompute: summaries for the assessment, topic summaries, attention flags for the
offering. Return counts. Dashboard refetches.

14. AI Copilot Architecture (V3)
The LLM never sees raw tables and never computes a number; it chooses from a fixed set
of analytics tools and writes prose around their outputs.
sequenceDiagram
  participant F as Faculty
  participant C as Copilot service
  participant L as LLM
  participant A as Analytics API
  F->>C: Which students in Sec B struggle with recursion?
  C->>L: question + tool schemas + user scope
  L->>C: call get_topic_weak_students(offering=B, topic=Recursion)
  C->>A: scoped call (same RBAC as UI)
  A->>C: 11 students, avg 38%, threshold 40%
  C->>L: tool result JSON
  L->>C: draft answer

  C->>F: answer + tool calls + links
14.1 Components
Intent + slot resolution: LLM function-calling picks a tool; names like "Section B" and
"recursion" are resolved to IDs by a deterministic resolver against the user's accessible
offerings/topics (not by the LLM guessing IDs).
Tool registry (~8 tools): get_offering_summary , get_topic_performance ,
get_weak_students(topic) , compare_assessments(a1, a2) , compare_sections ,
get_student_profile , get_attention_list , get_intervention_outcome . Each
wraps an existing analytics service — zero new maths.
Scope enforcement: tools run as the logged-in user; a faculty cannot query another
faculty's section through the copilot.
Number verifier: regex-extract numbers from the answer; every number must match a
value in tool outputs (± rounding). Fail → regenerate once, then return the tool data as
a table with no narrative.
Refusal path: questions outside tools ("predict who will fail", "rank faculty") → polite
fixed response listing what it can answer.
"Why did Section B decline?" is answered as where it declined (topic-wise deltas
CT1→CT2, largest drops) — the system states correlation, not cause.
Privacy: send register numbers + first names only when needed; log question, tools
called, and latency in ai_query_logs , not full student data.
Provider: any tool-calling LLM API; keep the client behind an interface so the model
can be swapped. Budget ~$5 of API credit for dev + demo.

Four people stay unblocked through three frozen contracts (schema, OpenAPI,

19.1 Contracts frozen in Week 1
Database contract: M1 merges all models by end of Week 1. After that, schema

edit a merged migration.
API contract: every MVP endpoint exists as a stub returning example data by end of
Week 1 (FastAPI + Pydantic models). Frontend generates types from /openapi.json .
